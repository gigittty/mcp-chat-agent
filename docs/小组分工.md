### 为什么这么切

- **工具层按「要不要画图」分成两块**：`calc/weather/todo/files/fun_pick` 都是「拿到数据 → 返回文本」，共享 `sandbox` 和 `net` 两个基础设施；而 `chart/meme/ascii_art` 全都依赖字体探测和中文字形渲染，是一条独立的技术线。这样切开后两个人几乎不会碰同一个文件。
- **规划器与界面归一人**：`PlanDecision` 是两者的契约，同一个人改起来不用来回沟通。
- **MCP 与集成测试归一人**：协议层最容易出「本地能跑、换台机器就跑不起来」的问题，让写协议的人自己守测试最有效。
- **文档与生图归一人**：博文里最需要配图，`make_meme` / `make_chart` 的产出直接就是文章素材。

## 协作方式

| 环节 | 做法 |
|---|---|
| 需求与设计 | 全组一起定「八个工具 + 两种规划器 + 两条通道」的骨架，再按模块分头实现 |
| 接口约定 | 先定 `ToolSpec` / `ToolResult` / `PlanDecision` 三个数据结构，各模块只依赖这三样，所以可以并行开发 |
| 代码合并 | 由谢嘉鸿统一 review 并提交，保证每次提交都能跑、`pytest` 全绿 |
| 测试归属 | 每个模块的实现者写自己的单测；集成测试（MCP 端到端、网页）由林炳辉负责 |
| 文档 | 黄国轩汇总，各模块负责人提供自己那部分的「踩坑记录」（见 `成员心得.md`） |
| 演示材料 | 张志远录屏与截图，黄国轩负责排版进博文 |

## 提交与分工的对应关系

代码统一由谢嘉鸿执行 `git commit`，但**每次提交按模块聚合**（个别提交会包含两个人的产出，
例如契约层与测试骨架就一起提），所以提交历史仍能反查出分工：

```bash
git log --oneline -- 3124004444/agent/tools/chart.py   # 查生图模块是谁做的
git log --oneline -- 3124004444/mcp_server/            # 查 MCP 层是谁做的
```
